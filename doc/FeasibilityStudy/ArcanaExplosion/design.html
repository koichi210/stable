ArcanaExplosion 設計図

トランプ52枚がキャラクターとアイテムに化けるカードバトル（Python＋Flask＋HTML/JS）の内部設計。
アーキテクチャ・シーケンス図・ステートマシン図・ER図を、ソースコードの実装に合わせて描いています。

  1. アーキテクチャ（全体構成・動かし方の3パターン）
  2. シーケンス図（CPU対戦／LAN対戦／攻撃1回の内部処理）
  3. ステートマシン図（部屋の一生／ターン進行／画面遷移）
  4. ER図（メモリ上のデータモデル）
  5. この設計図の育て方

1. アーキテクチャ

ルール本体（engine/）・HTTPの入り口（server/）・画面（web/）の3層に分かれていて、 ルールを知っているのは engine だけ。画面は「今できる操作」をサーバーから actions 配列で受け取り、ボタンに変えるだけです。

設計の約束ごと

約束どう実現しているかうれしいこと
ルールとUIを分けるengine/ は Flask もブラウザも import しない。simulate.py と server/ が同じ Game を使う画面を作り直してもルールは無傷。CPU同士を何百戦も回してバランス検証できる
相手の手札はサーバーで落とす返す盤面は必ず Game.view(seat) を通す。相手側は hand_count だけ、伏せ札のログは LogEntry.private_to で絞る通信を覗いてもカンニングできない
画面はルールを知らない「今できる操作」は legal_actions() が作り、actions 配列で画面に届くルールを変えてもJSを直さなくていい
数値はコードに書かないすべて balance.json。スキンごとの例外だけ balance_overridesPythonを読まずにバランス調整できる
CPU戦もLAN戦も同じ「部屋」違いは席1に座るのがCPUか人間かだけ（Room.mode）通信・再接続・再戦の仕組みが1つで済む

2. シーケンス図

2-1. CPU対戦：部屋を作って1手指すまで

CPUの手は1手ずつ画面が取りに行きます（cpu_step）。まとめて1ターン進めると、届くのは終わった後の盤面だけになり、攻撃モーションを出せないからです。

2-2. LAN対戦：部屋作成 → 参加 → 対戦中の同期

WebSocket は使わず、1.2秒ごとのポーリングで相手の操作を拾います。盤面に変化が無ければ rev を比べて小さな返事（unchanged: true）だけ返します。

sequenceDiagram
  autonumber
  participant H as ホストのブラウザ（席0）
  participant S as サーバー（app.py＋Room）
  participant J as 参加者のブラウザ（席1）

  H->>S: POST /api/room/create（mode=lan, name, skin, options）
  S-->>H: 合言葉4文字・token0（ゲームはまだ無い）
  H->>H: 待機画面に合言葉を表示

  loop 1.2秒ごと（相手待ち）
    H->>S: GET /api/room/state?code&token
    S-->>H: room.waiting = true
  end

  loop 2秒ごと（部屋さがし画面）
    J->>S: GET /api/room/list
    S-->>J: 相手待ちのLAN部屋の一覧
  end

  J->>S: POST /api/room/join（code, name, skin, options）
  S->>S: token1 を発行 → 2人そろったので _start_game()（rev+1）
  S-->>J: token1・seat=1・view(1)
  J->>J: 対戦画面へ

  H->>S: GET /api/room/state（次のポーリング）
  S-->>H: waiting = false の盤面
  H->>H: 対戦画面へ（enterGame）

  Note over H,J: ここから対戦。どちらも1.2秒ごとに ?rev=今の番号 を付けて聞く

  H->>S: POST /api/room/action（自分の番の操作）
  S->>S: 部屋の鍵（RLock）を取って Game を更新、rev+1
  S-->>H: view(0)

  J->>S: GET /api/room/state?rev=古い番号
  S-->>J: 新しい盤面 view(1)（相手の手札は枚数だけ）
  J->>J: 演出を再生して描画

  J->>S: GET /api/room/state?rev=最新
  S-->>J: unchanged = true（部屋情報だけ）

  Note over S: 15秒アクセスが無い席は「切断中」と表示
部屋が404を4回続けたらロビーへ戻す

対応ソース：web/js/flow.js（poll・joinRoom・refreshRoomList）、server/rooms.py（join・view・opponent_online）

2-3. サーバー内部：攻撃1回で起きること

攻撃1回が、撃破 → トレーナーへのダメージ → 勝敗判定 → 繰り上げ待ち まで連鎖します。トレーナーHPを減らすのは必ず _damage_trainer で、減らした直後に勝敗を見るので「相打ち」は起きません。

sequenceDiagram
  autonumber
  participant R as Room.apply
  participant G as Game
  participant C as CombatMixin

  R->>G: apply_action(attack, seat)
  G->>G: pending_choice / pending_promote / 手番 をチェック
  G->>C: _act_attack → _do_attack(p, o)
  alt 相手のバトル場が空
    C->>C: _damage_trainer（直接攻撃）
  else 相手キャラがいる
    C->>C: ダメージ = max(最低ダメージ, 攻撃 − 防御)
    C->>C: 攻撃時の技（毒・疲労・範囲攻撃 など）
    C->>C: _damage_character（シールドで軽減 → HPを減らす）
    opt HP が 0 以下
      C->>C: _defeat（不死鳥なら1回だけ復活）
      C->>C: _damage_trainer（撃破ダメージ30）→ _check_end
      C->>G: _remove → _refill_field
      G->>G: ベンチがいれば pending_promote に席を積む（人間は選ぶまで停止）
    end
  end
  opt まだ決着していない
    C->>C: 反動 → 疲労・攻撃回数カウント（3回で強制退場）
  end
  G->>G: _check_end → _trim_bench → _snapshot（リプレイ用に両者の view を保存）
  G-->>R: true
  R->>R: rev += 1、決着なら finished_at を記録

対応ソース：engine/game.py（apply_action・_act_attack・_refill_field）、engine/combat.py（_do_attack・_damage_character・_defeat・_post_attack_upkeep）

3. ステートマシン図

3-1. 部屋（Room）の一生

部屋の掃除は「作ってからの時間」ではなく「最後に誰かが見に来てからの時間」で判定します。長い対戦の途中で部屋が消えないようにするためです。

stateDiagram-v2
  [*] --> 相手待ち: create（mode=lan）
  [*] --> 対戦中: create（mode=cpu）
すぐ start_game

  相手待ち --> 対戦中: join（2人目が入る）
  相手待ち --> 削除: やめる（ホストが leave）
  相手待ち --> 削除: ホストが5分来ない（WAITING_TTL）

  対戦中 --> 決着: winner が決まる
finished_at を記録
  対戦中 --> 削除: 誰も3時間来ない（ROOM_TTL）

  決着 --> 対戦中: rematch（もう1試合）
game_no+1
  決着 --> 削除: 決着から30分（FINISHED_TTL）
  決着 --> 削除: 誰も3時間来ない

  削除 --> [*]

  note right of 対戦中
    サーバーの再起動・Renderのスリープでも
    すべての部屋は消える（メモリ上だけ）
  end note

対応ソース：server/rooms.py（RoomRegistry._cleanup・close・Room.join・rematch）。掃除は部屋の作成時と一覧取得時に走ります。

3-2. ゲームの進行（ターン）

1ターンは「ターン開始の自動処理」→「行動フェーズ」→「ターン終了処理」の繰り返し。行動フェーズの途中で、めくって選ぶ待ちとバトル場の繰り上げ待ちが割り込みます。

カードの持ち主とスキン

  • 🃏 キャラクターの山札は1人1箱。持ち主のスキンで作るので、相手と違うスキンでも自分のカードは自分の見た目のまま。
  • 🎒 アイテムの山札は2人で共有の1箱。手札に入った瞬間（_draw_item）に引いた人のスキンで作り直す。
  • 🌩️ 第三勢力の山札は各スキンの魔神軍を混ぜた専用山札。公開時は非公開スキンの代わりにオリジナル版を使う。

5. この設計図の育て方

  • 図はすべて Mermaid のテキストで書いてあります。このHTMLの <pre class="mermaid"> の中を直せば図が変わります。
  • 各図の下の「対応ソース」が、図の元になった関数です。そこを変えたら図も見直してください。
  • ルールの数値（HP・ダメージなど）は balance.json が正本です。図の数字とずれたら balance.json のほうが正しいです。
  • この図はゲーム本体から自動では更新されません。ゲーム側のリファクタのあとは手で合わせます。
